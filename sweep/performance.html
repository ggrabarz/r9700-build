    Measured performance¶

    These numbers are not all the same kind of number

    A build entry's figure can be measured (harness, prompt set), self-reported (one run, the owner's tool), vendor-published, or a ceiling the owner reads as a regression. The registry labels every one. This page groups them so you can see the bands; it is not a leaderboard.

    The bands, in plain terms¶

    If you are planning a single quad for a small team, the corpus supports these planning numbers:

    Workload Realistic sustained Aggressive (MTP, tuned image, high concurrency)
    27B dense FP8/MXFP4 80–150 t/s single-stream 236 t/s (B14), 900 t/s aggregate @16 (B1)
    Flash-Next class 100–150 t/s single-stream 478 @C8 (B29), 580 @8 (B46), 813.9 @C8 (B27)
    122B MoE / gpt-oss-120b 40–90 t/s 213 aggregate (B13), 651 @c16 (B40)
    DeepSeek-V4 (2–3 bpw) 20–79 t/s 79 (B7), ~48 floor (B43)
    Long context (251k+) 137–154 t/s flat (B45) 23.7 at 262k on a 122B (B48)

    The honest per-GPU number for a general 27B service is 42–47 tok/s/GPU (B3's production box, B27's 813.9 across four cards at C8) — not the 236–1,192 headline, which is 16 concurrent streams on a 122 GB TR PRO box with a tuned Radiance stack.

    Concurrency behaviour¶

    The corpus contains several full scaling curves, and they disagree in a useful way:

    Build Shape c1 c4 c8 c16
    B14 Flash-Next, Radiance 236 591 890 1,192
    B26 Flash-Next, lab 102.2 — 437.8 —
    B40 35B FP8 43 — — 651
    B13 122B GPTQ 49 — — 213
    B37 27B Q4, llama.cpp 45.0 90.8 73.3 —
    B49 Flash-Next, no P2P 117.89 — — —

    Two patterns worth noting:

    • Aggregate rises, per-stream falls. B1's 27B drops from 900 t/s at 4k/user to 80 at 128k/user with 16 sessions — context length, not card count, sets the per-stream rate.
    • MTP aggregates can invert. B37's llama.cpp box peaks at c4 (90.8) and falls to 73.3 at c8; B26's vLLM box rolls over after c8→c16. "More concurrency" is not monotonic on these cards once speculative decoding is in play.

    Prefill¶

    Prefill is where the quad shines and where the platform matters least:

    Build Prefill Context
    B4 17,636 t/s short
    B41 8,105 t/s Flash-Next
    B29 7,400 t/s C8, PCIe 3
    B27 7,025 t/s aggregate 4k prompts, C8
    B1 6,880 t/s per user 48k/user, 16 sessions
    B32 6,320 t/s 142k
    B45 5,892–6,307 t/s 1k–251k
    B41 316 t/s Gen3 x1 — the cliff

    A Gen3 x16 host (B45) and a Gen5 TR PRO (B1) sit in the same prefill band. A Gen3 x1 host loses ~16× (B41). Width, not generation.

    Latency, where it was published¶

    Only one entry publishes a distribution rather than a point:

    B27 — Qwen3.8-27B FP8, 8 parallel requests, 4k prompt:

    • TTFT mean 4.605 s (P50 4.674, P90 4.682, P95 4.683, P99 4.690)
    • TPOT mean 9.93 ms (P50 10.00, P99 11.62)
    • End-to-end mean 9.677 s (P99 10.550 s)

    Everything else is a tok/s figure, often without a prompt set — which is why the registry treats cross-entry comparisons as indicative only.

    What is not measured¶

    • No controlled TP4 vs 2×TP2 A/B on one host with one prompt set. B14 claims Radiance TP4 beats 2×TP2 by ~45%; nobody has reproduced it independently.
    • No long-context TP4 latency curve beyond B45's batch-1 table and B48's single X post.
    • No TTFT distribution except B27.
    • No SGLang TP4 performance at all — correctness only (FlagOS fork, TP_SIZE=4, all validations passed).
    • No benchmark for the two OEM quads (B51, B52).
