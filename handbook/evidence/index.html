    Evidence & corrections¶

    This page is the audit trail. It records what was believed, what replaced it, and why — so a later session does not re-make the same mistake. Nothing here is deleted from the project; superseded claims are marked, not hidden.

    1. How a claim earns a place in this handbook¶

    Tag Test it passed
    MEASURED A published run on R9700 hardware, with the model, quant and context named.
    REPORTED The builder's own claim without an independent run. Usable, labelled.
    DERIVED Arithmetic on measured inputs (cost per token, residency, lane counts).
    VERIFIED Checked against a primary artefact: vendor manual, spec sheet, config file, source code.
    UNKNOWN No source found. It stays UNKNOWN; it is never silently upgraded.

    The rule that decides disputes: the primary source wins over an agent, and a measurement wins over vendor documentation. That rule is not theoretical — it is how iommu=pt was caught, and how the brief's own bandwidth figure was corrected before any downstream number used it.

    Every load-bearing fact was read at least twice: once by the supervisor from the primary source, once by an agent from its own source. research/09-verification-matrix.md records the 14 contradictions that survived that process.

    2. The corrections that changed the design¶

    2.1 The brief's memory bandwidth was wrong by 2.8×¶

    Value Consequence
    Shared brief (illustrative) 32 GB GDDR6, 512-bit, 1.792 TB/s Would make the PCIe fabric, not DRAM, the decode bottleneck
    AMD product page (all eight agents + supervisor) 256-bit, 640 GB/s Decode is DRAM-bound at every realistic batch size

    This is the single most important correction in the project. At 1.792 TB/s the whole PCIe-vs-DRAM argument inverts. The corrected figure is at the top of research/00-supervisor-verification.md and research/08 §0, and no downstream number uses the wrong one. VERIFIED.

    2.2 DeepSeek V4.1 Flash's KV cache: 46–120 KB/token → 890 bytes/token¶

    A8 derived 46–120 KB/token from the raw MLA dimensions. A7 read the model card and DeepSeek's technical report (arXiv 2609.19969) and got 890 bytes/token of global KV.

    A7 is right. The raw-dimension derivation ignores three mechanisms:

    1. CSA2 cross-layer KV reuse — compress_ratios [0,0, 2×18, 1×18, 0,0], kv_source_layer_ids [2,8,14,20].
    2. FP4 KV caching — E2M1 main KV + indexer K, one E4M3 scale per 16 channels.
    3. SWA in every layer — only the first two encoder layers are pure SWA.

    At 1 M tokens the global KV is 890 MB, not tens of gigabytes. The persistent SWA KV, not the global KV, is the scaling term. Corrected in docs/SPECS.md §5/§7.1 and the animation. VERIFIED.

    2.3 The V100 estimate was wrong by 18×¶

    The three-platform comparison initially modelled V100 throughput from bandwidth and got ~950–1,500 tok/s on GLM-5.3-Flash. A late-returning subagent found two independent 2026 8-card V100 corpora; the measured figure is 53.0 tok/s aggregate.

    Estimate Measured
    V100 GLM-5.3-Flash ~950–1,500 tok/s 53.0 tok/s
    V100 complete machine $13,988 DIY $8,500–$9,000 (warrantied Supermicro 4029GP-TVRT)
    V100 3-year TCO $24,059 $19,045

    Why the estimate failed: V100 has no native FP8 or FP4. It must dequantise NVFP4 into FP16 on 2017 tensor cores, so it spends its time converting rather than multiplying. The NVLink fabric was never the bottleneck; precision support was. The project had guessed the opposite. All three comparison files were corrected. MEASURED.

    2.4 iommu=pt: the vendor doc loses to the measurement¶

    AMD's ROCm system requirements say multi-GPU systems "may require iommu=pt … to prevent application hangs." On a real 2× R9700 box, with iommu=pt on, peer READ returns 0xFF garbage and peer WRITE is silently dropped.

    The measured fix is to remove iommu=pt and leave the IOMMU translated. The brief's runbook, the architecture doc and the animation all carried the vendor advice and were corrected. This is the highest-consequence item in the runbook: the failure mode moves from a loud hang to silent data corruption. MEASURED.

    2.5 Kimi K3's expert shape: 3 × 7168 × 3072 → 3 × 3584 × 3072¶

    A8 assumed experts run at the full hidden width. A5 read config.json and modeling_kimi_linear.py and found routed_expert_hidden_size = 3584 — a LatentMoE latent. Each expert is 3 × 3584 × 3072 = 33,030,144 params; 92 MoE layers × 896 experts = 2.7227 T routed-expert parameters. Verified against shard-header tensor shapes, not just the config. A8's conclusion (≈6× the box's VRAM) is unaffected; the arithmetic is now A5's. VERIFIED.

    2.6 GLM-5.3-Flash and GLM-5.3 are different models¶

    A sibling's single "GLM 5.3 = 45 layers, 288 experts" conflated two architectures:

    Model Class Shape
    GLM-5.3-Flash Glm5NextForConditionalGeneration (glm5_next) 45 layers, 288 routed + 1 shared, 3 dense-MLP lead + 34 KDA linear + 11 MLA+DSA
    GLM-5.3 (full) GlmMoeDsaForCausalLM (glm_moe_dsa) 78 layers, H 6144, 256 routed experts, all full-attention DSA, no linear layers

    Treating them as one model produces a wrong layer split. They are separate rows in docs/SPECS.md §7 and separate entries in the animation. VERIFIED.

    2.7 DeepSeek V4.1 Flash's layer pattern: "16 full-attn of 40" → 36 global¶

    A8 read compress_ratios and concluded 16 full-attention layers. A7 quoted the same array — [0, 0, 2×18, 1×18, 0, 0] — meaning layers 0–1 SWA, 2–19 ratio 2 (Full), 20–37 ratio 1 (Reuse/Reindex), 38–39 ratio 0. 36 layers carry a global branch; only the first two encoder layers are pure SWA. The animation now uses the exact index range 2–37. VERIFIED.

    2.8 WRX90E-SAGE SE: "ruled out" → "7 × x16 plus one bifurcated slot"¶

    A1's TL;DR said the board "can NOT host 8 × x16: 6 × x16 + 1 × x16@x8 — option ruled out." Its own cost table described a bifurcated x8/x8 build with 7 × x16 slots. The accurate statement: 7 × x16, and the eighth GPU occupies one slot split into 2 × x8 — viable, with one GPU at half width. Corrected in docs/ARCHITECTURE.md §2.1. VERIFIED.

    2.9 The memory price range → itemised October 2026 street price¶

    A1's TL;DR gave "8 × 64 GB at $3.6k–7.2k+" (a trend range). Its final cost table gives the dated, itemised price: 8 × 64 GB DDR5-6400 at $2,799.99 each = $22,400, and 8 × 32 GB DDR5-5600 at ~$950 each = $7,600. The itemised table wins. The $14,800 delta between 256 GB and 512 GB is now called out as the largest controllable cost in the build. VERIFIED.

    2.10 INT4: the instruction exists, the kernel does not¶

    A1 verified in the LLVM ROCDL definitions that gfx1201's WMMA stack includes v_wmma_i32_16x16x32_iu4 (K = 32) — the instruction behind the card's 766 TOPS INT4 dense peak. A3 found that no shipping kernel emits it on gfx1201; every 4-bit path (AWQ, GPTQ, GGML Q4_K) dequantises to FP16/int8 first. A3's mnemonic guess (16x16x16_iu4) was flagged unverified; A1's 16x16x32_iu4 is the verified one.

    Both are right and complementary. It does not change the 4-bit conclusion (bandwidth-bound either way), but it identifies the highest-leverage unclaimed optimisation on this part. VERIFIED.

    2.11 The all-reduce tax is latency, not bytes¶

    The early framing emphasised bytes. The final measurement: at TP=8 the all-reduce moves only 10,240–14,336 B per layer, so 80–186 collectives per token is 0.49–2.67 MB/token — 81–164 µs of link time, ~0.4 % of a 20 ms token. The real cost is 2.6–6.1 ms of synchronisation: 5–31 % of a token, and 20.9 % in the measured GLM TP=8 profile (46 collectives × 27.3 µs = 1.26 ms).

    The latency framing is the stronger one because it survives the objection that the byte count is small. The architecture doc now leads with it; the animation has a SYNC POINTS / TOKEN panel. MEASURED + DERIVED.

    2.12 A8's final revision changed three more conclusions¶

    • Qwen3.8-27B at FP8 is 27.78 GB and fits on ONE 32 GB card (13.89 GB at INT4). The dense model wants one GPU per replica, not eight-way sharding.
    • The VRAM-residency break-even: ≥ 43.5 % of the active routed-expert bytes must be resident for 20 tok/s (≥ 73.7 % for 50 tok/s), because dense weights and the shared expert are always resident and cannot be streamed. This sizes the expert cache, not the model size.
    • Flash economics changed: at 15.36 TB per drive, enterprise Gen5 (PM1743) is $287/TB at its best channel, cheaper than a consumer 4 TB SN8100 at $300/TB, and adds 1 DWPD + PLP + hot-swap. But the datasheet 14.0 GB/s falls to ~7.0 GB/s at the 0.5× sustained derate, and DDR5 memcpy costs 4× an SSD read — so eight Gen5 drives need 384 GB/s of DRAM traffic, over an 8-channel DDR5-4800 budget. The recommendation became capacity-driven.

    5. Claims deliberately left UNKNOWN¶

    These are recorded as open. Filling them with a guess would have been worse than leaving them.

    1. Exact street price of the ASRock Rack TURIND8X-2T/500W and GIGABYTE G494-series boards (quote-only SKUs); EPYC 9575F/9655F/9755F street prices.
    2. Whether HSA_NO_SCRATCH_RECLAIM=1 helps on gfx1201 (AMD documents it only for gfx90a).
    3. RCCL CollNet / Tree performance on a PCIe-only 8 × gfx1201 node — AMD publishes no numbers. Partly moot at TP=2, where Radiance's one-shot all-reduce sidesteps RCCL.
    4. The ROMED8-2T/BCM PCIe lane map — which of PCIE1/3/5/7 are CPU-direct, and whether all four support PCIe atomics. This is a correctness gate for TP=2, not a footnote.
    5. Whether 640 GB/s is still achievable at the 210 W cap. The guide never ran a card at 300 W; Puget's 310 W for two cards at c=1 shows the cap does not bind at low concurrency.
    6. Multi-node AMD without RDMA — not found in any source. Assume unusable. This got more important when the answer to "8 GPUs" became two quads, which must talk over ordinary Ethernet.
    7. Whether the G494-SB0 boards are validated for the non-S R9700 (the manual lists the R9700S only).
    8. hipFile direct-to-GPU on gfx1201 with consumer M.2; no storage vendor has announced certified hipFile/AIS support for ROCm 10.1.
    9. SGLang HiCache on Radeon with the file L3 backend, and whether its GPU-assisted kernel I/O backend is available on ROCm.
    10. Which Kimi the build guide actually tested, and the result. "Kimi" appears exactly once in 93 pages, with no version, method or outcome. Deliberately not guessed.
    11. Whether the DSA indexer kernels exist for ROCm/gfx1201 at all — scorer, top-k/radix select, sparse latent attention, hybrid memory manager, KDA chunked kernels.
    12. Whether vLLM-Radiance carries a Kimi K3 path (vllm.models.kimi_k3.amd plus AITER SiTUv2 a4w4 on gfx1201). No evidence that it does.
    13. The dspark acceptance behaviour on gfx1201, and the hc_head parameters for the SGLang path.
    14. The exact QSA indexer KV-cache bytes and GDN state for Qwen3.8-Flash-Next at 1 M context — not published.
    15. A measured TP=8 path for Qwen3.8-Flash-Next; a controlled TP=8 vs 4 × TP=2 comparison; a long-context TP=8 latency number; an RCCL busbw number for 8 consumer gfx1201 cards.

    6. What would change the verdict¶

    The current answer is two proven quads. These are the conditions that would flip it, with the threshold where the arithmetic actually turns.

    Flip condition Threshold Why
    GLM-5.3-Flash becomes a material share of traffic ≥ ~30 % of tokens at ≤ 128 K context That is the octo's only exclusive workload; below it, the 20.9 % sync tax and +17 % $/GPU dominate
    A >128 GB working set becomes material Flash-Next or a larger MoE in steady production The quad runs it at a 31.62 GB deficit; the octo has 96.4 GB headroom — but needs a measured TP=8 path that does not exist yet
    A 48 GB R9700-class card appears ≤ ~$2,000 At 384 GB total VRAM, Kimi K3 (330 GB) fits entirely and the octo becomes structurally necessary
    A validated 8-card air chassis ships Any retail SKU Today the only validated 8-card build is liquid R9700S, and no retail waterblock exists for the Creator card
    DeepSeek V4.1 Flash's software ships vllm#57491 + dspark executing on gfx1201 Then the octo becomes feasible at $17.30/Mtok Gen4 — a wash, not a win
    DDR5 prices fall 32 GB RDIMM back near $300 The octo's BOM is disproportionately exposed to DDR5; the quad uses DDR4-2666
    Multi-node without RDMA becomes viable A measured AMD multi-node path Two quads are the answer partly because the alternative is one big failure domain

    7. The agent-route problem (reproducibility note)¶

    This does not affect the findings, but it explains why some sessions produced nothing and why the archive has empty threads.

    Attempt Route Outcome
    T3 delegate_task on openrouter/* qwen3.8 / kimi-k3 / glm-5.3 / deepseek-v4.1 Blocked by a workspace guardrail — "N endpoints excluded". Family-scoped; does not clear on its own
    T3 delegate_task on opencode/* — A server restart killed the tool surface mid-run; run bookkeeping went stale
    Native subagent on freellmapi/* kimi-k3, glm-5.3, deepseek-v4.1-flash, qwen3.8-27b Silent death — empty assistant message, zero tool calls, zero output, while the route reads "ready" on the gateway
    Native subagent on opencode/* zen routes beam-free, flint-40b-free, mimo-v2.6, glm-5.3 Working — own quota, reliable one-word probe
    Three-platform wave six agents on freellmapi / xkiro / logfare Five died on account-wide budget exhaustion; the sixth returned late with the V100 data that overturned the estimate

    The rule that works: probe every candidate model with a one-word prompt before committing a brief. A route that reads "ready" is not evidence that it will answer.

    The practical consequence for this archive: a thread with 0 assistant messages is a route that died before its first token, not a session that chose to do nothing. The output file may still exist because a later route or the supervisor wrote it.
