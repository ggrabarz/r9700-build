    Gotchas¶

    Every item here cost at least one debugging session on real R9700 hardware. They are ordered by how quietly they fail, not by how often they appear. A crash is cheap; a wrong number that looks plausible is expensive.

    Tags follow the handbook convention: MEASURED, REPORTED, DERIVED, VERIFIED, UNKNOWN.

    1. The five silent-corruption traps¶

    These do not crash. They return wrong answers, or they return right answers at a fraction of the expected speed, and nothing in the logs says so.

    # Trap What you see What is actually happening Fix Evidence
    1 iommu=pt on the kernel command line Runs fine; peer reads return 0xFF garbage and peer writes are dropped The IOMMU in passthrough mode breaks P2P on gfx1201. AMD's ROCm docs recommend iommu=pt for multi-GPU; the measurement contradicts the doc Remove iommu=pt. Leave the IOMMU in translated mode MEASURED on a 2× R9700 box — docs/ARCHITECTURE.md §2; research/09-verification-matrix.md §2.12
    2 Forcing AITER linear at TP ≥ 2 Garbage tokens, NaNs, or an immediate accuracy collapse gfx1201's gemm_a8w8_blockscale picks NUM_KSPLIT=8 for small M. At TP=2 with per-rank K = 12,800, the 1,600 split is not a multiple of BLOCK_SIZE_K, so the reduction reads past the tile Do not force AITER linear when per-rank K is not a multiple of 1024. Validate output on any AITER run MEASURED — vllm-project/vllm#28649 (xy7ra)
    3 Relaxed start barrier in a custom all-reduce Every all-reduce returns stale data; 500/500 wrong at TP=2, 4 and 8 On non-coherent PCIe, the release/acquire barrier is what makes the peer buffer visible. A relaxed barrier lets the read race the write Use a release/acquire start barrier. This — not "TP>2 is broken" — is the real cause of the garbage-TP folklore MEASURED — vllm-project/vllm#61848, B30
    4 A card's BAR0 above the 44-bit DMA mask hipMemcpyPeer, D2D hipMemcpy and torch.Tensor.copy_ exit 139 instead of returning an error amdgpu_device_is_peer_accessible() rejects destinations above 2^44; KFD records peer access in one direction only Print hipDeviceCanAccessPeer for every pair and each card's BAR0 base before blaming the engine. In a VM, set cpu: host,guest-phys-bits=44 MEASURED — ROCm/rocm-systems#15102 (B33); fixed in L1T 254183
    5 Stale Triton / flashinfer / vLLM caches A recipe that works for everyone else hangs on your box, even with NCCL_PROTO=Simple already set The container reuses compiled kernels from an earlier image or driver Clear the caches before re-testing a recipe. One owner's "engine bug" was his own cache REPORTED — B42, L1T 250504

    The one that matters most

    iommu=pt is the only item in this handbook where AMD's own documentation is not the final word. The failure mode moves from a clean hang to silent data corruption. If you change one line in the runbook, change this one.

    Kernel HSA_AMD_P2P = Y On a two-card Supermicro H13SAE-MF, amd-smi topology read ENABLED on every peer while rocm-bandwidth-test returned N/A until the kernel was built with it. After: 28.1 GB/s unidirectional / 55.5 GB/s bidirectional L1T 251544

    2.1 Verify P2P before you trust it¶

    amd-smi topology showing every peer ENABLED is not proof of switch-local routing. On a PLX88096 quad, all four cards trained Gen4 x16, the topology table read ENABLED, and peer traffic still crossed the root complex at 14.25 GB/s unidirectional / 27.77 GB/s bidirectional — an effective ~32 GB/s cluster cap against 63 GB/s theoretical.

    # the only trustworthy check
rocm-bandwidth-test            # or TransferBench
amd-smi topology               # necessary, not sufficient

    Applying per-switch ACS overrides (acs-plx-switch-p2p.sh) fixed it on bare metal (+500 tok/s prefill on Flash-Next) but not inside QEMU. The RDNA4 ROCm DKMS module can also silently disable P2P independently of BIOS and atomics: the access table reads DISABLED on every peer even when AtomicOpsCtl: ReqEn+ is set on all cards. That needs a patched module, and in one case also a lower MMIO placement. (B34)

    Variable / flag Value Why Evidence

    NCCL_P2P_DISABLE / RCCL_NET Do not set Re-adding either undoes P2P and lands you back on the host path B7 HOWTO

    --kv-cache-dtype fp8 when MTP is on MTP + BF16 KV corrupts tool calls at TP=4 in at least one production recipe B42
    --gpu-memory-utilization 0.85–0.97 depending on recipe Too high starves the graph capture; too low wastes KV B42, B44

    3.1 The 192 KiB all-reduce cliff¶

    Custom one-shot all-reduce on RDNA4 has a hard dispatch limit at TP=4:

    Message size One-shot RCCL Winner
    8 KiB 8.4 µs 18.2 µs one-shot, 2.2×
    32 KiB 13.1 µs 33.8 µs one-shot, 2.6×
    256 KiB 52.0 µs 49.4 µs RCCL

    Below 192 KiB the one-shot kernel wins by up to 2.6× per call; at and above it RCCL wins. This is why "custom all-reduce is faster" and "custom all-reduce is slower" are both true on the same box. (vllm#61848, B30)

    3.2 Do not stop at three cards¶

    On 3× R9700 (9950X + ProArt X870E-CREATOR, Gen5 x8 + x4, third card on an M.2 adapter) vLLM fails the model head division check on Qwen3.8-Flash-Next. Three cards cannot use that path at all. The practical ladder is 1 → 4, not 1 → 2 → 3 → 4. (L1T 245308 #37)

    And on a host with no P2P, adding the second card can make things slower: a dense 31B runs 25.2 tok/s on one card, but a 2-card tensor split falls to 18.8–19.4 (−23 %) because the reduction crosses the host. The same four cards at TP4 reach 39.8 tok/s. (B49)

    4. Power and thermals¶

    Trap Detail Evidence
    The cap is not optional Uncapped cards hard power-off ~7 minutes into warm-up. 210 W costs almost nothing: dual-card decode 151.5 vs 153.0 tok/s at 210 vs 300 W (+1 % for +50 % power) MEASURED — B19, u/notyours
    Capping can double throughput gpt-oss-120b TP4: 44.6 → 89.4 tok/s after the 210 W cap. amdgpu.ras_enable=0 separately took another box 40 → 97 tok/s MEASURED — B19
    The card spikes past its cap ~400 W transient despite a 210/300 W setting; an 850 W PSU is insufficient for two cards B19; build guide
    PSU load steps Radiance's custom all-reduce creates multi-kHz in-phase load steps that trip some ATX 3.x supplies. BeQuiet Dark Power 14 1200 W fails; Thermaltake GF3 1650 W, Lian Li 1000/1200 SFX, Corsair HX1200i, Seasonic 2200 W are proven B14, B7
    Connector count is a vendor choice PowerColor ships a 2× 6-pin → 12VHPWR adapter; other vendors consume 3× 8-pin. A four-card PowerColor box needs 8 PCIe feeds instead of 12 L1T 239508 #63
    120 V branch limit 19.3 A at 120 V at the 210 W cap; 25.9 A at 300 W. Two circuits or 240 V for an octo OCTO-VERDICT §2
    Chassis slot arithmetic Four dual-slot cards need 8 expansion slots; many boards, including big Threadripper boards, have 7 NoobFeed B39
    OEM server PSUs are rated per card A Gigabyte G291-Z20 rated 300 W/card crashed individual cards on spikes; the 210 W cap did not fix it; only one card per dual bay did B37
    Thermals are chassis-dependent, not universal One quad hit 100 °C hotspot at a 250 W cap; another holds 69–70 °C at 100 % load and 300 W in "cramped" spacing lcz 1936; B46
    Stock fan curve pauses work It follows the CPU, not the cards. Set a software curve that reacts at 62 °C Build guide p.114

    4.1 The octo has no cooling path you can buy¶

    • Four cards at 210 W in 4U air already hit a 68 °C card-area pause and 81–90 °C junctions.
    • The only validated 8-card build is the liquid R9700S.
    • No retail waterblock exists for the Creator card. Alphacool's 1-slot block lists ASRock Creator, ASUS TURBO, PowerColor and Sapphire — not Gigabyte.
    • Community verdict: blocks are for >4 cards; a 4-card air box that fits with airflow is the lower-risk choice.

    This is the one risk that time does not fix. Every other octo objection is performance or software; this one is a part you cannot order. (OCTO-VERDICT §9)

    5. Topology and lanes¶

    Trap Detail Evidence
    "8 × x16" is false The single-socket lane map is 7 × x16 + 1 × x8 + 2 × NVMe x4 = 128 lanes, with no PCIe switch. Manual-verified OCTO-VERDICT §5.1
    No NVLink, no xGMI Every GPU↔GPU byte crosses PCIe. Many small TP groups beat one large one: DP × TP=2, never one TP=8 group docs/ARCHITECTURE.md §2
    Gen4 in practice The cards link at PCIe 4.0 x16, not Gen5: 28.4 GB/s measured; Puget independently measured 27.6 GB/s P2P Build guide; Puget
    PCIe has a floor, and it is x1 Four cards at Gen3 x1: 316 tok/s prefill / 50 decode on a 27B, against 5,187 / 118 at Gen4 x16 — a 16× prefill loss. x4–x8 is tolerable; one lane is not B41
    A PLX switch is not a bypass See §2.1 B34
    One-way P2P is a SIGSEGV, not an error See trap 4 B33
    Sync tax does not shrink with bandwidth 46 collectives × 27.3 µs = 1.26 ms = 20.9 % of every GLM token at TP=8 OCTO-VERDICT §2
    4 KV heads cap TP Qwen3.8-27B has 4 KV heads; TP>4 replicates KV (8.0 GiB/seq/card). TP=8 is refused by name (missing gqa3) config.json; Radiance
    2 KV heads cap Flash-Next at TP=2 Clean sharding tops out at TP=2; vLLM uses expert parallel instead B3/guide

    6. RAM and storage sizing¶

    Trap Detail Evidence
    A bigger GPU does not lower the RAM a Strata model needs Strata's own model page: the model fits when RAM ≥ experts + ~10 GB. This is the single most expensive sizing mistake in the project Strata docs; docs/BEST-3-4X-R9700-BUILDS.md
    128 GB is a real ceiling At 128 GB the Strata ceiling is UD-Q5_K_XL; Q6_K_XL (118 GB) and Q8_0 (136 GB) fall into --mmap-experts low-RAM mode, where one measured box spent 82 % of every token waiting on the host stream (36 → 79 tok/s only once experts were resident) B6
    8 × 256 GB RAID0 is the wrong array 256 GB drives have 2–4 NAND packages (~2–3.5 GB/s each); eight ≈ 16–28 GB/s — the same as two 2 TB Gen5 drives, at 4× the lanes and 4× the failure domains. DeepSeek packs are 239–274 GB, so 2 TB is thin Strata review, 321464d6
    One NVMe is enough for the proven build The production quad uses one 1 TB 990 PRO. A multi-SSD array costs 3.29× the whole machine Build guide
    The PLE table must be in RAM, not on disk Moving it from disk to RAM took one 3-card box from 5–7k to 24k prefill. The quads show the same from the other side: B45 keeps int6 PLE on NVMe with an 8 GB cache and gets 5.2–6.3k PP; B26 reserves ~51 GB of host RAM; B14 pins a 47.7 GiB n-gram table r/R9700 1xojild; B45, B26, B14
    Eight Gen5 drives do not fit the DRAM budget They need 384 GB/s of DRAM traffic — over an 8-channel DDR5-4800 budget. The naive 224 GB/s stream is 131 % of DDR4-2666 A8 final revision; OCTO-VERDICT
    NVMe is a capacity tier, not a bandwidth tier DDR5 memcpy costs 4× an SSD read (2× with zero-copy). Streaming from disk is the fallback, not the plan A8

    7. Model and engine refusals¶

    These are not tuning problems. The engine refuses the configuration.

    8. Operational traps¶

    Trap Detail Evidence
    Do not mix vendors in one TP group Adding an RTX 4500 Ada lost throughput on every model tested; an R9700 alone beat R9700 + 7800 XT r/LocalLLaMA 1xhq12y, 1xcpbqd
    Six cards is the wrong number TP works at 2/4/8; 1,200 W of GPU already sits near a 120 V branch limit 1pkrnpo; B20
    Bare metal is the supported path VFIO/KVM can hang at ncclCommInitRank. Puget's earlier "multi-GPU vLLM fails" was a KVM/VFIO artifact, later retracted. If you must virtualise, pass only the GPU functions and set guest-phys-bits=44 Puget; L1T 254183
    A 100k+ conversation cache is a crash surface 9 SDMA gfxhub page faults in 3 days on a production box, all on host-VA snapshot copies; disabling the conversation cache stopped it Strata#4591, B32
    Stale image tags can cap throughput One owner's single-session decode is capped at ~70 tok/s on every tcclaviger image from 29.06.19 on; 29.05.2 has no cap but has MTP/SSE tool-call trouble. A tag-level regression, not a config error B44
    A hang can be a cache, not a kernel Wendell's Approach A hung with NCCL_PROTO=Simple already set; he traced it to his own stale Triton/flashinfer/vLLM caches B42
    Fan service threshold Set the software curve to react at 62 °C; the 68 °C card-area warning is already a pause Build guide

    9. Myths, fakes and retracted claims¶

    Claim Reality Evidence
    "8 × x16 on one socket" 7 × x16 + 1 × x8 + 2 × NVMe x4 = 128 lanes, no switch Board manual; OCTO-VERDICT §5.1
    "Layer split beats TP on this box" Layer split wins on capacity, loses on throughput: llama.cpp plateaus at 56 tok/s where vLLM reaches 156–320 Puget
    "Strata is the only HIP engine validated on R9700" vLLM-Radiance / standalone Radiance is the production engine; Strata is the capacity/streaming engine Build guide; A2
    "FP4 does not exist on RDNA4, so MXFP4 is impossible" True of the silicon; MXFP4 is reachable as a Quark container and a W4A8 fp8-WMMA path A2/A3
    "RCCL fails on R9700" That case was a chipset x16 slot with no PCIe atomics. Stock vLLM TP=2 initialises RCCL in 0.12 s on a proper slot Puget retraction
    "A 4-card number from a vendor guide" One vendor retracted a 4× 50–80 tok/s figure in place; the current revision says 8× 30–35 tok/s. No host, no prompt set either way djdeniro commit 4f82b05
    "569 tok/s across 16 lanes" No card count attached; not promoted @HealthRanger reply
    A quad post with an AI-generated image Debunked and removed by the mods; the only r/AMD crosspost of it was removed under Rule 3 r/LocalAIServers 1xc8uxg
    amdai.net as a quad source A two-card, Cursor-agent-written, affiliate-monetised site sources/brane-technologies-r9700.md; amdai repo
    A benchmark without a bandwidth check Puget published and corrected a 1.9× error of its own, caught by a bandwidth-plausibility check. Apply that check to every R9700 number, including this handbook's Puget

    10. Pre-flight checklist¶

    Run this before you believe any number.

    [ ] nvidia-smi equivalent: amd-smi static --asic  -> 4 x gfx1201, 32 GB each
[ ] amd-smi metric --power                      -> cap reads 210 W on every card
[ ] cat /proc/cmdline                           -> NO iommu=pt
[ ] grep HSA_AMD_P2P /boot/config-$(uname -r)   -> =y
[ ] rocm-bandwidth-test                         -> every pair > 25 GB/s D2D
[ ] hipDeviceCanAccessPeer matrix               -> all 1s, both directions
[ ] echo $NCCL_PROTO                            -> Simple
[ ] echo $GPU_MAX_HW_QUEUES                     -> 1
[ ] rocm-smi --showtemp                         -> < 70 C under load, hotspot < 95 C
[ ] one 27B FP8 request, then check the output  -> not NaN, not repeated
[ ] one 262k-context request                    -> KV does not OOM
[ ] power draw at 16 users                      -> ~837 W for a proven quad

    If a run is faster than the bandwidth model allows, suspect the measurement before celebrating. That rule has already caught one vendor error and one of this project's own estimates.
