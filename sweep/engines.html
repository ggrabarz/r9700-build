    Engines and recipes¶

    Engine notes¶

    Stock vLLM is not a toy. B29 is the counter-example to the whole "you need a custom image" belief: stock vLLM 0.30 + stock ROCm 10 on a PCIe 3.0 host reached 478 tok/s at C8 and 7,400 tok/s prefill. If you are starting today, start there.

    Radiance is the performance path. The fork (and the standalone engine) is where the 236 → 1,192 numbers come from. Its 4-rank one-shot all-reduce was the missing kernel until brainchillz/r9700-tp4-allreduce added it (PR jdrews/vllm-mxfp4#2); before that TP=4 fell back to RCCL. The standalone engine's Docker Hub page now says vLLM is no longer maintained and work moved to codeberg.org/StillDeadcode/radiance — worth knowing before pinning stilldeadcode/vllm-radiance.

    llama.cpp is the compatibility path, not the speed path. It runs everywhere, splits by layer, and on PCIe often beats tensor split for MoE (97 vs 67 t/s on Gen5 x16 in one report). It also shows MTP aggregate inversion earlier than vLLM (B37 peaks at c4).

    Strata is the redundancy path. Its HAProxy topology (B15) is the production answer for failover, but on the same host it decodes 140–160 t/s where Radiance does 235 (B6), and its 4-card Flash-Next layer split segfaults on the first request in some builds (B31) while 2 cards serve at 87.5 t/s.

    SGLang moved from "unverified" to "correctness-verified, unbenchmarked". The FlagOS fork (FlagTree + FlagCX) runs TP_SIZE=4 on 4× R9700 and passes its own validation gate; the "Performance tuning" box is still unticked. Do not quote it as a throughput option.

    TP4 gotchas that cost days¶

    Interconnect and kernel

    • RCCL tuning-index bug on gfx1201 deadlocks TP≥2 → NCCL_PROTO=Simple.
    • hipIpcGetMemHandle: invalid argument on vLLM-ROCm ≥0.21 → HSA_ENABLE_IPC_MODE_LEGACY=0; do not re-add NCCL_P2P_DISABLE or RCCL_NET=Socket.
    • Custom all-reduce on RDNA4 has a 192 KiB dispatch limit at TP4: below it the one-shot kernel wins by up to 2.6× per call; at and above it RCCL wins. It also needs the release/acquire start barrier — with the old relaxed barrier on non-coherent PCIe, every all-reduce read stale data (500/500 wrong at TP=2/4/8), which is the real cause behind "TP>2 gives garbage on R9700".
    • GPU_MAX_HW_QUEUES=1 fixes a gfx1201 slow-dispatch state (6/8 boots; 139 → 210 t/s in one report). B49 saw 2.7× from it.
    • amdgpu.ras_enable=0 doubled throughput in one report (40 → 97 t/s).

    Model and quant

    • Qwen3.8-Flash-Next has only 2 KV heads → TP=4 duplicates half the KV cache. TP=2/PP=2 is the suggested shape; the 4-card box runs it, but pays for it.
    • AITER linear can silently emit NaN on TP≥2 when per-rank K is not a multiple of 1024 (gfx1201 split-K bug). Validate output on any AITER-linear run.
    • --tp-wire wht6 is not 6-bit at four ranks — it is a tiered int8 wire with a Hadamard rotation, lossy above 128 KiB messages. Measured against exact: same scores (80/80 arithmetic, 57/60 LiveCodeBench), ~2% prefill cost. exact is the safe default.
    • MTP + BF16 KV can corrupt tool calls at TP=4; one owner needed --kv-cache-dtype fp8.
    • Non-power-of-two card counts fail: vLLM refuses Flash-Next on 3 cards (model-head division check), and Saber refuses TP=3/4 by name. 2, 4, 8 are the shapes.

    Runtime hygiene

    • Stale container caches can look exactly like an engine bug. One owner's hang persisted with NCCL_PROTO=Simple already set and vanished after clearing Triton/flashinfer/vLLM caches.
    • A throughput cap can come from an image tag, not the hardware: B44 saw ~70 t/s from tcclaviger tag 29.06.19 onward, while 29.05.2 did not cap.
    • shm_broadcast TimeoutError on the first request with aml731/vllm-aiter — try the 0.19 tag or drop MTP first.
