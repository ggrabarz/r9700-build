    Quantisation¶

    RDNA4's usable lattice is FP16 / BF16 / FP8 / INT8. FP6 and FP4 do not exist on this silicon. Every model that ships in FP4 — DeepSeek's experts, Kimi K3's entire release — must be dequantised on the fly or repacked. That single fact decides which models are servable and which are capacity toys.

    1. The instruction map¶

    Weight format RDNA4 path Effective ceiling Verdict
    FP16 / BF16 v_wmma_f32_16x16x16_f16 191 TFLOPS (4× the 47.8 vector FP16) reference path
    FP8 (E4M3/E5M2) v_wmma_{f32,f16}_16x16x16_fp8_bf8 383 TFLOPS the best supported dense path
    INT8 v_wmma_i32_16x16x16_iu8 383 TOPS published; 45.8 TFLOPS measured = 12 % of peak works, underutilised
    INT4 v_wmma_i32_16x16x32_iu4 (K=32) 766 TOPS published the instruction exists; no shipping kernel emits it. Every 4-bit path dequantises to FP16/int8 first
    FP6 / FP4 absent — no 16x16x128_f8f6f4 on gfx1201 — CDNA-only
    3-bit / 2-bit GGUF dequant + int8 MMQ bandwidth-bound what Strata ships

    The highest-leverage unclaimed optimisation on this part is an INT4-WMMA expert kernel for gfx1201. It would move the 4-bit expert path off dequantise-to-FP16 entirely. TileLang is the practical language for it (CUDA-first, but the one DeepSeek repo with a second backend).

    2. The crossover that decides decode¶

    The bandwidth/compute crossover sits at M ≈ 300 rows per GEMM for every precision (FP16 298, FP8/INT8 299, INT4 299), because peak scales with bit-width while DRAM does not.

    At the 210 W operating cap the crossover falls to M ≈ 210, because core clock drops with the power cap while memory clock does not.

    Two consequences:

    1. Decode is far below either number, so decode is bandwidth-bound and no instruction choice rescues it. The levers are resident-expert hit rate, bit-width, working-set placement, and a cheap dequant→dot path.
    2. A power-limited card is relatively more compute-rich, not more bandwidth-bound. At the same M it sits further past the crossover. FP4 buys decode time in proportion to bytes saved, not merely footprint.

    Measured proof: the R9700 expert-cache read hits 637–640 GB/s — the full DRAM ceiling. The GPU is already maxed on memory.

    3. What each format is actually good for¶

    FP8 — the default¶

    • Native, 383 TFLOPS, and what the frontier MoE models are designed around.
    • Qwen3.8-27B's own FP8 checkpoint is 27.8 GB; BF16 is 55.56 GB and does not fit with 262 K KV.
    • FP8 KV cache is load-bearing: 2.12 M tokens on 2 × 32 GiB, 5.6× BF16.
    • BF16 KV + MTP at TP=4 can corrupt tool calls. One owner needed --kv-cache-dtype fp8 or "tool calls go haywire with MTP". Use FP8 KV.

    INT8 — works, but not the fast path¶

    • 383 TOPS published but 45.8 TFLOPS measured = 12 % of peak. The kernels are not tuned for it.
    • No reason to choose it over FP8 on this part.

    INT4 / MXFP4 — reachable, but not native¶

    • No FP4 WMMA. MXFP4 is reachable in two ways:
    • as a container format (Quark), dequantised into FP8/INT8 on the fly;
    • as a W4A8 fp8-WMMA path at 325 TFLOP/s in Radiance.
    • Every 4-bit GGUF (IQ2/IQ3/Q2_K/Q4) runs dequant + int8 MMQ. It is bandwidth-bound and that is fine for decode, which is bandwidth-bound anyway.
    • The gap is in prefill, where the missing fused dequant+matmul costs real time.

    3-bit GGUF — the capacity format¶

    • GLM-5.3-Flash at 3-bit is 117.5 GB and fits 4 × 32 GB entirely. That is the configuration that removes the host-RAM bottleneck.
    • Qwen3.8-Flash-Next at IQ3 is the smallest practical 125 B-class pack.
    • Kimi K3's smallest GGUF is 330 GB — already larger than 256 GB of VRAM. Bit-width cannot rescue a 6.1× gap.

    4. KV cache: the numbers per model¶

    Model KV per token At 262,144 tokens Note
    Qwen3.8-27B 64 KiB 4.0 GiB/card at TP=2, FP8 16 full-attention layers; the rest linear
    GLM-5.3-Flash 768 elements/token/layer 1.18 GiB/card at 256 K in Q8_0 (4.43 GiB f32 on two cards) plus 142 MiB/sequence KDA state, constant
    DeepSeek V4.1 Flash 890 B/token global 890 MB at 1 M tokens CSA2 + FP4 KV + SWA; the weights are the problem
    Kimi K3 27,648 B/token MLA + fixed KDA ~7.2 GiB + ~429 MiB/sequence 57.4 GiB/rank at 8 × 262 K — over a 32 GB card before weights
    Qwen3.8-Flash-Next not published at 1 M — QSA indexer + GDN state; the exact bytes are UNKNOWN

    The rule: compute per-card KV at the target context and concurrency before choosing the quant. A profile that fits at 32 K often does not at 262 K, and the failure is a load-time refusal or an OOM — not a slowdown.

    5. Quantisation decisions by model¶

    Model Recommended Why
    Qwen3.8-27B FP8 weights + FP8 KV + MTP native, fits, measured; BF16 does not fit
    Qwen3.8-Flash-Next MXFP4 (Quark) on Radiance, or IQ3 GGUF on Strata 125 B + 51 B n-gram; PLE table dominates
    GLM-5.3-Flash 3-bit GSQ-RCO (Q2_K experts) + Q4_K MTP, Q8_0 caches 117.5 GB fits entirely; router/indexer/mHC/KDA/MLA stay F32/BF16
    DeepSeek V4.1 Flash Strata ISTA 2.00–2.875 bpw packs 510 GB FP8 is not viable; Engram alone is 183 GiB
    Kimi K3 none 330 GB minimum; not a serving target
    gpt-oss-120b MXFP4/Quark BF16 runs at 0.2 tok/s at TP4

    6. Traps that cost output, not speed¶

    • AITER linear can silently emit NaN at TP≥2 when per-rank K is not a multiple of 1024. The gfx1201 gemm_a8w8_blockscale uses NUM_KSPLIT=8 for M≤8; at TP=2 with K=12800 the split 1600 is not a multiple of BLOCK_SIZE_K → NaN. Validate output on any AITER-linear run. With the split-K fix, Qwen3-32B-FP8 went 25.8 / 71.1 / 182.5 → 27.2 / 78.0 / 204.3 tok/s at c1/c3/c8.
    • The hipBLASLt tuning table is valid only for the exact (architecture, hipBLASLt version) pair. Matching: 1.84× on a 2048-token prompt. Mismatched: ~0 %. Version-lock the container or lose prefill silently.
    • A quantisation that changes accuracy is not free. B3's builder measured an FP8-vs-MXFP4 accuracy trade on the same box. Any low-bit pack needs a task-level check, not just a tok/s number.
    • Full-layer MXFP4 on an unsupported path produces token salad. One owner had to hand-fix an MLP-only quantisation; the full-layer version failed.

    7. The measurement rule for every quantisation claim¶

    If the implied bandwidth exceeds 640 GB/s per card, the number is wrong.

    A single card cannot read a 27 B-parameter model faster than 640 GB/s ÷ 27 GB ≈ 23 tok/s at 100 % memory utilisation. No caching, batching or kernel choice changes that arithmetic.

    Puget shipped a DeepSeek throughput number 1.9× too high because its harness counted output tokens with the wrong tokenizer. They caught it with exactly this check: "our previously-reported 61.7 tok/s on a 16 GB model would require about 991 GB/s of memory bandwidth, but the R9700 has 640 GB/s." Apply the check to every number in this handbook, including the ones that flatter the platform.
